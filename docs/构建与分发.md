# 构建与离线分发（I06）

本文件说明通用组件库如何从 `src/manifests/*.json` 生成可离线使用的全量包、模块包、registry 和自包含预览。构建器只用 Node 内置模块，不安装依赖、不访问网络、不需要运行时服务。

## 1. 命令

在组件库根目录（含 `scripts/`、`src/`、`vendor/`）执行：

```bash
# 开发构建：缺失的模块/ID 只警告，适合并行开发
node scripts/build.mjs

# 严格构建：105 ID、各模块 manifest、源文件、demo、gallery 预览任一缺失即失败
node scripts/build.mjs --final

# 严格构建并把单文件预览复制到发布位置（默认 dist/组件库-预览-发布.html）
node scripts/build.mjs --final --release

# 静态核对（默认严格）
node scripts/check.mjs

# 开发期部分模块尚未到位时，只对缺失项降级为警告
node scripts/check.mjs --partial

# 生成公共编排层整合单文件离线预览（默认 dist/公共编排层-整合预览.html，模板 examples/demo-scene/standalone.html）
node scripts/build-demo-preview.mjs

# 生成作者装配与聚焦预览（README 入口，模板 examples/authoring/index.html）
node scripts/build-demo-preview.mjs --template examples/authoring/index.html --output dist/作者装配与聚焦-预览.html

# 生成复用验证（矩阵乘法）预览（模板 examples/reuse-matrix-product/standalone.html）
node scripts/build-demo-preview.mjs --template examples/reuse-matrix-product/standalone.html --output dist/公共层复用验证-矩阵乘法.html

# 生成自定义图形示例预览（模板 examples/propagation/index.html）
node scripts/build-demo-preview.mjs --template examples/propagation/index.html --output dist/传播过程与局部过渡-预览.html

# 生成最小连续画面示例预览（模板 examples/continuous-scene/index.html）
node scripts/build-demo-preview.mjs --template examples/continuous-scene/index.html --output dist/连续画面局部变化-预览.html

# 生成流程与连接图形中性示例预览（模板 examples/flow-kit/index.html）
node scripts/build-demo-preview.mjs --template examples/flow-kit/index.html --output dist/图形扩展-中性示例.html

# 生成流程组合配方预览（模板 examples/flow-composition/index.html）
node scripts/build-demo-preview.mjs --template examples/flow-composition/index.html --output dist/流程组合-预览.html

# 生成完整整合候选 ZIP（默认 dist/公共编排层-整合候选.zip）
pwsh -File scripts/package.ps1
```

可选参数：

| 参数 | 含义 |
| --- | --- |
| `--root <dir>` | 组件库根目录；默认是本脚本上一级，由 `import.meta.url` 计算，不写死机器路径 |
| `--out <dir>` | 产物目录；默认 `<root>/dist` |
| `--release-target <file>` | `--release` 的目标文件；默认 `<root>/dist/组件库-预览-发布.html`（在 note 内） |
| `--final` | 严格模式；必需输入缺失或预览未就绪时以非零码退出 |
| `--release` | 要求已生成单文件预览且本次构建无错误，按字节复制到目标，并回读比较；失败时不复制 |

`node scripts/build-demo-preview.mjs` 默认读取 `examples/demo-scene/standalone.html`，把 src/styles/脚本内联为单文件 `dist/公共编排层-整合预览.html`；支持 `--template <file>` 与 `--output <file>`（旧 `examples/demo-runtime/standalone.html` 仍可用显式参数生成）。

开发构建可以成功退出但带警告；严格构建和 `check.mjs` 用非零退出码报告失败。`--release` 只复制文件，不发布、不上传、不提交版本库。

### 1.1 确定性与重复运行

- 输入按固定模块顺序、固定 manifest 文件名排序与固定源文件顺序拼接；不依赖当前目录或机器绝对路径。
- dist 文件头不带时间戳，源文件只做必要换行归一，不做会变化的 minify/hash。
- `registry.json` / `dist/registry.js` 需要记录构建时间。默认取当前时间；需要字节级复现时设置 `BUILD_TIMESTAMP=<ISO 时间>` 或 `SOURCE_DATE_EPOCH=<秒>`。除此之外，相同输入产生相同结构、顺序与内容。
- 每次构建会先清理已知的旧产物（`dist/note-library.*`、`dist/modules/`、`dist/registry.js`、`dist/组件库-预览.html`），再写新文件；不要手改 `dist/` 或根 `registry.json`。
- 即使指定 `--out`，构建仍会更新根 `registry.json` 与 `dist/registry.js`；局部验证请用一次性临时根或等同步阶段统一执行，避免把开发构建产物留在正式位置。

## 2. 输入与校验

### 2.1 manifest

每个模块在 `src/manifests/` 写一个或多个 JSON，例如：

```json
{
  "module": "ui-layout",
  "title": "布局与容器",
  "js": ["src/ui/layout.js"],
  "css": ["src/ui/layout.css"],
  "demos": ["gallery/demos/ui-layout.js"],
  "dependencies": ["core"],
  "entries": [
    {
      "id": "L01",
      "name": "NoteUI.Container",
      "cn": "内容容器",
      "category": "布局与容器",
      "purpose": "……",
      "inputs": ["maxWidth", "padding", "align", "content"],
      "customizable": ["……"],
      "states": ["……"],
      "usage": "NoteUI.Container.mount(host, {...})",
      "dependencies": ["core"],
      "limitations": ["……"],
      "userReview": "not-reviewed",
      "reviewScope": "适用范围说明",
      "consensus": ["K08", "K11", "K16"],
      "docs": "docs/ui-layout.md#L01"
    }
  ]
}
```

- `module` 必须是固定模块之一。一个模块可由多个 `blocks-*.json` 等文件合并，条目按 manifest 文件名与数组顺序合并。
- 条目的必需字段：ID、公开名称、中文名、类别、用途、输入、用法、依赖、限制、userReview、reviewScope、共识、文档。可选 `customizable`、`states`、`notes`、`source`、`dist`、`demo`、`preview`、`example`。
- 类别与 expected-ids 中的类别必须一致；`userReview` 只接受 `not-reviewed` / `positive-with-scope` / `rejected`。
- **manifest 不写技术状态。** 技术状态与验证依据只来自 `src/status.json`；构建不会因为“文件存在”把 planned 提升成 implemented 或 verified。
- 全部模块的维护源位于根目录src；R01–R10也使用根内路径。archive中的旧组不再是构建输入，不能恢复兄弟目录依赖。
- 模块顺序与 core/legacy 内部顺序集中在 `scripts/lib/source-order.mjs`，构建、静态核对与 tests 的源码加载 harness 共用同一份顺序。manifest 的 js 数组顺序就是经典脚本加载顺序；拆分源码时必须按顺序把新文件写入数组，构建会照数组拼接。

### 2.2 105 ID

`scripts/expected-ids.json` 是 ID 数量和类别的唯一对照：R10 + 78 新组件 + B10 + I7 = 105。构建检查：

- 105 个 ID 全部有条目、无重复、无未知 ID；
- 每个条目的类别匹配；
- 模块源文件和 demo 文件存在；
- 每个条目的 source/dist 路径存在（dist 在构建后由 `check.mjs` 复核）；
- 开发模式缺失项只警告，`--final` 失败。

### 2.3 gallery 未就绪

单文件预览从 `gallery/index.html` 真实构建。开发期若 gallery 外壳、脚本或图片尚未到位，构建会明确警告并跳过预览；`--final` 将其视为错误。构建不会伪造预览，也不会复制一份手写页面。

## 4. 加载顺序与模块依赖

### 4.1 固定顺序

全量 JS 和全量 CSS 严格按：

```text
core → legacy → ui-layout → ui-content → ui-actions → ui-navigation →
ui-forms-basic → ui-forms-advanced → ui-overlay → ui-feedback → ui-extended →
viz-objects → viz-flow → viz-mechanisms → viz-chart → blocks-base → demo-stage → blocks → demo-runtime → demo-ui
```

特殊内部顺序：

- core JS：`core.js` → `icons-data.js` → `icons.js` → `motion.js` → `floating.js`
- core CSS：`tokens.css` → `base.css`
- legacy JS：controls.js → primitives.js → focus.js → range.js → link.js → sequence-insert.js
- legacy CSS：controls.css → primitives.css → focus.css → range.css → link.css → sequence-insert.css → legacy-bridge.css
- ui-content JS：content.js → table.js → expression.js；CSS：content.css → table.css → expression.css
- ui-forms-advanced JS：forms-advanced-internal.js → slider.js → forms-advanced.js → forms-advanced-pickers.js → forms-advanced-inputs.js；CSS：forms-advanced.css → slider.css
- viz-flow JS：flow-core.js → flow-stage.js → flow-packet.js → flow-segment.js → flow-device.js → flow.js；CSS：flow.css
- blocks：`blocks-base`（shared.js）→ `demo-stage`（B01）→ `blocks`（B02–B10）；blocks 模块内部按 blocks-stage.json / blocks-explain.json 合并后的 js 顺序加载

legacy **不使用**旧的 `note-ui.css`；旧 tokens 不进入新分发，tokens 只来自 core。其他模块内部源文件顺序按 manifest 数组，构建不擅自重排。

### 4.2 依赖表

下表是构建与分发约定；每个 `dist/modules/<module>.js|css` 文件头的 `dependencies:` 行与 `registry.modules[].dependencies` 是机器可读的最终依据。加载某个模块时，应加载 core 以及该模块声明的其他依赖模块。

| 模块 | 依赖 | 说明 |
| --- | --- | --- |
| `core` | 无 | NoteCore、tokens、icons、motion、floating；必须先加载 |
| `legacy` | core | R01–R10 旧组件；bridge 在此模块 CSS 末尾 |
| `ui-layout` | core | 布局与容器 |
| `ui-content` | core、vendor | 内容模块；JS 内嵌 marked+KaTeX，CSS 前含字体内嵌 KaTeX CSS |
| `ui-actions` | core、legacy | 操作扩展消费 Button |
| `ui-navigation` | core | 导航与定位 |
| `ui-forms-basic` | core | 基础表单 |
| `ui-forms-advanced` | core、ui-forms-basic | 高级表单复用基础字段与错误样式 |
| `ui-overlay` | core、legacy | 浮层消费旧 Button/基础浮层 |
| `ui-feedback` | core | 反馈与状态 |
| `ui-extended` | core、ui-navigation | 通用扩展；X05 TreeSelect 额外复用 TreeView |
| `viz-objects` | core | 图形对象 |
| `viz-flow` | core | 阶段轨、消息流、分段长度条、设备连接独立图形 |
| `viz-mechanisms` | core | 变化机制 |
| `viz-chart` | core | 基础统计图 |
| `blocks-base` | core | B01–B10 共用内部 helper（src/blocks/shared.js，不是公开 API） |
| `demo-stage` | core、legacy、ui-layout、blocks-base | B01 DemoStage；默认舞台只依赖它，不带入 B02–B10 |
| `blocks` | core、legacy、ui-layout、ui-content、ui-navigation、viz-objects、viz-chart、blocks-base、viz-flow、demo-stage | B02–B10 组合块；blocks-*.json 合并，依赖取并集并写入模块头/registry |
| `demo-runtime` | core | NoteDemo.create、scene、内置 Adapter、sceneAdapter、timingFacts |
| `demo-ui` | core、legacy、ui-layout、demo-stage、demo-runtime | 默认舞台与呈现；不依赖完整 blocks |

若模块源码内部调用其他模块的公开 API，manifest 必须显式声明，不能依赖全量包“碰巧都加载”。加载 `legacy` 只需 core；加载 `ui-actions` 需 core + legacy。各模块的 JS 是经典脚本（IIFE），不是 ES module。

### 4.3 取用方式

全量：

```html
<link rel="stylesheet" href="./dist/note-library.css">
<script src="./dist/note-library.js"></script>
```

只取一个模块（示例为布局）：

```html
<link rel="stylesheet" href="./dist/modules/core.css">
<link rel="stylesheet" href="./dist/modules/ui-layout.css">
<script src="./dist/modules/core.js"></script>
<script src="./dist/modules/ui-layout.js"></script>
```

`ui-content` 还需要按其模块头加载标记的 vendor 能力，但 vendor 已包含在该模块文件中：

```html
<link rel="stylesheet" href="./dist/modules/core.css">
<link rel="stylesheet" href="./dist/modules/ui-content.css">
<script src="./dist/modules/core.js"></script>
<script src="./dist/modules/ui-content.js"></script>
```

只取单个条目：构建器不做 tree-shaking。可依据 registry 条目的 `source` 找到维护源，并使用条目所在模块；模块包仍包含该模块其他条目。R条目使用src下的统一维护源；archive/prototypes中的旧独立包只保留来路，不是当前取用入口。所有路径均支持 `file://` 双击打开。

## 5. Vendor 与 KaTeX 字体内嵌

仅使用本地化的：

| 资源 | 版本 | 许可 | 进入位置 |
| --- | --- | --- | --- |
| marked | 18.1.2 | MIT | `ui-content` 模块 JS、全量 JS，core 之后、content.js 之前，只注入一次 |
| KaTeX | 0.19.1 | MIT | `ui-content` 模块 JS/CSS、全量 JS/CSS；CSS 字体内嵌，只注入一次 |
| Lucide | 1.62.0 | ISC | 由 `scripts/gen-icons.mjs` 生成 `src/core/icons-data.js`，随 core 分发 |

完整许可文本与来源见根 `THIRD_PARTY_NOTICES.md` 和 `vendor/*/LICENSE`。构建不下载资源，不把 CDN 地址写入运行文件。分发 ZIP/目录时应同时保留 vendor 许可文件。

KaTeX 处理规则：

- 只保留 `@font-face` 的 `.woff2`，转成 `data:font/woff2;base64,...`；
- 移除 `.woff` / `.ttf` 源引用；
- 产物不得残留 `fonts/...` 或外部字体 URL；
- 全量 CSS 的 KaTeX CSS 位于 `ui-content` 模块 CSS 之前；`ui-content` 模块 CSS 也自带，所以单独取内容模块也有公式字体；
- 其他模块不重复打包 marked/KaTeX。

## 6. 单文件预览生成

`dist/组件库-预览.html` 是对 `gallery/index.html` 的真实构建，不是手写副本：

1. 读取 gallery HTML 与相对路径资源。
2. 本地 `<link rel="stylesheet" href="...">` → 内联 `<style>`；CSS 内本地 `url(...)`（字体、图片）→ data URI。相对路径按该 CSS 文件所在目录解析。
3. 本地 `<script src="...">` → 内联 `<script>`。移除 `src`、`async`、`defer`、integrity/crossorigin 等属性，保持内联后的文档顺序。
4. 本地 `<img src>` / `srcset` 和与图片相关的静态资源 → data URI。
5. 本地内联 `<style>` 与 `style="..."` 中的本地 `url(...)` 同样内联。
6. `examples/assets/` 下的图片、字体以 data URI 映射注入一个极小的运行时 shim。demo 在运行时通过 `setAttribute` 或 `img.src` 设置这些示例素材时，写入的是 data URI，而不是相对文件；C08 通过路径构造的示例 SVG 因此也能在单独复制的预览中显示。这个 shim 只处理已知的示例素材，不是通用资源代理。
7. 移除 `<base>`，因为单文件内联依赖明确的相对解析；把指向文件外部的 `<a href>` 改成页内 `#`，避免单文件预览留下本地文件或外部页面入口。
8. 若 gallery 引用了外部 `http(s)` 样式/脚本/图片/字体，或资源缺失，预览不写出：开发模式警告，`--final` 失败。
9. 写出后再次静态检查：不能有 `<script src>`、`<link rel="stylesheet" href>`、本地非 data `img`、外部 URL、本地 CSS `url()`、`@import`、未解析的 `fonts/`。

限制：

- 只内联已知的静态 HTML/CSS 引用；运行时临时拼出的 URL、XHR/fetch 数据、ES module 动态导入、本地 `@import` 不在生成器能力内（gallery 不应使用）。
- 内联脚本仍是经典脚本；不支持 `type="module"` 的顺序语义。
- 被中和的非页内链接会失去跳转；这是离线单文件的明确取舍，正文路径来自 gallery。
- KaTeX CSS 的字体已内嵌，不依赖 `vendor/katex/fonts/` 随单文件分发。
- `--release` 只在单文件成功生成且构建无错误时按字节复制，不重新构建；发布文件与 dist 版本一致。目标默认是 `dist/组件库-预览-发布.html`，相对组件库根计算，避免写死机器路径。

## 7. registry 字段

根 `registry.json` 与 `dist/registry.js` 内容相同（后者加 `window.NOTE_LIBRARY_REGISTRY =` 包装）。顶层：

```json
{
  "schemaVersion": 1,
  "generatedBy": "scripts/build.mjs",
  "build": {
    "time": "ISO-8601",
    "mode": "development | final",
    "command": "node scripts/build.mjs ...",
    "moduleOrder": ["core", "legacy", "..."],
    "outputDir": "dist",
    "outputs": ["dist/note-library.js", "..."],
    "vendor": { "marked": "18.1.2", "katex": "0.19.1", "lucide": "1.62.0" }
  },
  "statusLegend": { "...": "来自 src/status.json" },
  "counts": {
    "total": 0,
    "expected": 105,
    "missing": 0,
    "extra": 0,
    "byStatus": { "planned": 0, "implemented": 0, "verified": 0, "blocked": 0 },
    "byCategory": { "...": 0 }
  },
  "missingIds": [],
  "modules": [],
  "entries": []
}
```

`entries` 每条至少含：

| 字段 | 含义 |
| --- | --- |
| `id`、`name`、`cn`、`category`、`module` | ID、公开名称、中文名、类别、所属模块 |
| `purpose`、`inputs`、`customizable`、`states` | 用途、可替换输入、可定制项、代表状态 |
| `usage` | 一行可运行用法 |
| `dependencies` | 条目的依赖说明 |
| `source` | 维护源（相对路径） |
| `dist` | 分发文件（模块包、全量包；I06 还含 registry/预览） |
| `demo`、`preview`、`example` | demo 函数位置（没有可视 demo 的共享基础条目为 `null`）、gallery 锚点、示例锚点 |
| `limitations` | 支持范围/限制 |
| `status`、`verification` | 技术状态、验证依据；只从 `src/status.json` 复制，构建不推断 |
| `userReview`、`reviewScope` | 用户评价档位与范围 |
| `consensus`、`docs`、`notes` | 共识引用、文档、补充记录 |

`counts` 只统计实际写进 registry 的条目；`expected` 固定为 105，`missing` 是 expected-ids 中尚无条目的数量。开发构建的 `counts.total` 小于 105 是正常的，不能据此写“已交付”。`verified` 只表示技术核验，不表示用户认可。

## 8. 静态核对与工程检查

### 8.1 静态核对 `scripts/check.mjs`

在根 `registry.json` 已生成后运行，默认严格模式检查：

- expected-ids 105、registry 无重复/未知 ID、类别与模块 manifest 一致；
- 每条 registry 的 source/dist 文件真实存在；
- 每条 registry 的 docs 链接可定位：目标文档存在，锚点或为显式 `<a id="…">`，或与 GitHub 风格标题 slug 一致；文档改标题/锚点导致链接失效会报错；
- manifest 声明了 demo 文件的模块，其每个条目在 demo 文件中确有对应函数定义；没有可视演示的共享基础条目允许 `demo:null`；
- 模块包文件头含 `note-library module`、正确模块名与依赖；全量包有两类头；
- 全量/模块 JS 可被 `new Function` 编译为经典脚本；registry/demo JS 语法同样检查；
- 无全局 `fetch()`、无 `eval()`、无 XMLHttpRequest/WebSocket/sendBeacon、无外部运行资源属性；KaTeX 内部的 `token.fetch()` 是解析器方法，不是网络 fetch；
- CSS 无 `@import`、无本地/外部非 data `url()`、无未解析 `fonts/`；
- registry 的 status / verification 与 `src/status.json` 逐项一致；
- counts 与实际 entries 一致；缺失 IDs 列表一致；
- 单文件预览不含 `<script src>`、样式表链接、非 data 图片/资源、外部 URL、本地 CSS `url()`、`@import` 或 `fonts/`；
- R01–R06 的 userReview 为 `not-reviewed`，R07–R10 为 `positive-with-scope`；R/I06 共识引用与合同一致。

`--partial` 只把缺失的预期 ID/模块、尚未生成的预览和缺失的 demo 文件降级为警告，已存在数据的结构错误仍失败；它不能替代最终的严格检查。构建/静态检查不替代真实 Edge 交互验收。

### 8.2 浏览器交互检查

这些检查不在 `build.mjs` / `check.mjs` 内，使用本机 Edge 与 `tests/tools/node_modules/playwright-core`：

```powershell
node tests/demo/core-check.mjs
node tests/demo/adapters-check.mjs
node tests/demo/ui-check.mjs
node tests/demo/integration-check.mjs
node tests/checks/public-transition-check.mjs
node tests/checks/source-loaders-check.mjs
node tests/checks/focus-continuity-check.mjs
node tests/checks/groups-check.mjs
node tests/checks/v05-assembly-check.mjs
node tests/checks/handoff-check.mjs
node tests/checks/authoring-page-smoke.mjs
node tests/checks/propagation-example-check.mjs
node tests/checks/flow-kit-check.mjs
node tests/checks/flow-scene-check.mjs
node tests/checks/flow-geometry-check.mjs
node tests/checks/stable-layout-check.mjs
node tests/checks/attention-composition-check.mjs
node tests/checks/query-cli-check.mjs
node tests/checks/query-closure-host-check.mjs
```

`handoff-check.mjs` 用普通 DOM 最小 fixture 验证视觉交接 v3 契约：`PreparedChange.sourceElements()` 在 prepare 后、commit 前调用一次并在观察期保持来源可见；`EffectSpec.handoff:'hold'` 的末帧保持到 scene 收束（动画结束到 idle 前不闪回）；handoff 只对该 spec 设置 fill:both；progress 声明 handoff 与未知 handoff 取值被定位拒绝；取消恢复来源停点、减少动效直接落终态。\`authoring-page-smoke.mjs\` 对 \`examples/authoring/index.html\` 第三例（普通 DOM 交接）做页级轻量 smoke：观察期来源可见、完成后目标接住且无残留内联样式、动画结束到 idle 不回落、取消回 source、reduced 直落终态；依赖已重建的 \`dist/\`。

代表检查覆盖范围：`focus-continuity-check` 覆盖 Focus weak/restore/reanchor、会话 Focus 复用与默认舞台 replayPreviousStep 映射；`groups-check` 覆盖 attention 观察目标/效果组/range/联合依赖拒绝；`v05-assembly-check` 覆盖 Range offset、Field/NumberInput 外部 slot 与 Notice 内容契约；`propagation-example-check` 加载 `examples/propagation/index.html` 验证同一 Binding 依据观察→分组放行、历史层不覆盖与取消/重看，并按帧采样 label/tick/event 在动画结束后不闪回、观察期来源对象可见、焦点框包住真实前沿/事件对象；它依赖已重建的 `dist/`。

`source-loaders-check.mjs` 是纯静态核对：检查 examples 与 tests 的 HTML 夹具是否按 manifest 顺序加载了全部必要 src 脚本、是否引用了已不存在的源文件。模块拆分后先跑它，再跑依赖浏览器的检查。

- `flow-kit-check.mjs` 直载 `core + viz-flow`，验证四个独立图形、稳定 ID/update、StageTrack 目标/旁路、PacketFlow `visibleCount` 显现、SegmentBar 零长度/尺度与 DeviceLinks 路径采样。`flow-scene-check.mjs` 验证 table 与四个 flow Adapter、拆分入口与 Propagation 的 mount/update/getTarget/destroy。
- `query-cli-check.mjs` 与 `query-closure-host-check.mjs` 验证查询 JSON、context key 与按 `模块依赖` 声明的闭包生成最小宿主（只加载对应 `dist/modules`）；`example:flow-kit`、table Adapter、flow-packet Adapter 与 `public:propagation` 的依赖以实际输出为准。
- 稳定布局以页面观察为主：PacketFlow 的 `layoutCount`/`visibleCount` 只改变显现、不改变视图行范围；StageTrack 的圆点/连接线/徽标槽变化在 `examples/flow-kit/index.html` 与 `examples/flow-composition/index.html` 中可直接核对。`flow-geometry-check.mjs` 量测圆点/连接线中心与 PacketFlow viewBox/宿主高度稳定；`stable-layout-check.mjs` 在流程组合预览的多宽度/多停点下检查文档坐标与高度；`attention-composition-check.mjs` 验证下段 attention 指向 `message:<id>`、表格/读数辅助同步与 reduced/取消。
- Table 的 `stableStateLabels` 默认 Standalone `false`、`table` Adapter `true`；每行常驻隐藏状态标签槽（无固定 min-height、不裁切正文，5 行表约 261→361px），可在流程组合预览中观察行高稳定，结合 `stable-layout-check.mjs` 回归。

- `tests/demo/*` 与 `tests/checks/public-transition-check.mjs` 直接加载 `src/` 经典脚本；源码清单由 `tests/lib/src-sources.mjs` 按 `src/manifests/*.json` 的模块与 js 数组顺序推导，模块拆分后无需逐个人工同步。HTML 夹具无法运行时读 manifest，由 `source-loaders-check.mjs` 防止顺序/漏载漂移。
- `tests/checks` 还保留各模块自检脚本与 HTML 夹具；夹具是输入，脚本里的静态扫描按 manifest 定位模块文件。
- 生成的截图、结果 JSON、日志与临时构建副本统一写入 `tests/.cache`（打包排除），`tests/checks` 只保留脚本与输入夹具；`tests/tools` 是本地驱动依赖，`tests/consumer` 是独立消费测试记录。

除上面列出的入口外，`tests/checks` 中的单模块脚本属于补充核验，可按受影响模块单独运行；它们与构建产物无关，失败不代表离线包不可用，但应在改动对应模块后重跑。

## 9. 已知限制与未验证

- 发布前应在全部模块完成后重跑 `node scripts/build.mjs --final --release`、`node scripts/check.mjs` 与受影响的浏览器检查；开发模式的部分产物不能作为最终发布包。用户评价与对外发布仍由维护者处理。
- `scripts/build.mjs` / `check.mjs` 只做文件、顺序、语法、静态离线性、registry 一致性与文档锚点检查；没有在每个浏览器中自动运行全部组件和检查布局观感。真实交互与视觉验收由 gallery 浏览器检查与人工观察负责。
- 浏览器检查依赖本机 Edge 与本地 playwright-core，未安装时无法运行；构建与静态核对不依赖它们。
- 不做 minify、tree-shaking、source map 或按条目拆分；模块文件包含该模块全部条目。KaTeX 字体使其 CSS 体积较大。
- 模块依赖由 manifest 声明，构建不对缺失的跨模块调用做运行期分析；声明错误需要负责人修正。
- 单文件预览不内联任意的运行时动态请求、ES module、局部 `@import`；gallery 必须使用可直接静态内联的本地资源。`examples/assets/` 的示例图片/字体是唯一带运行时 data URI shim 的目录；其他运行时构造的本地路径（例如文档/源码下载链接）在单文件中可能失效。
- 预览会对静态非页内锚点做 `#` 中和；如果需要保留外链，请在本库之外的发布页处理。gallery 运行时生成的文档/源码链接也应在发布时核对。
- 构建/预览只在当前桌面 Edge（Chromium）环境中实际双击与交互验证；Firefox/Safari、移动端、打印/PDF、非 `file://` 宿主未验证。
- 构建清单中的用户评价只记录现状，不代表审美确认；新增组件与 R01 新变体仍需用户评价。
- `--release` 目标目录可配置；发布、上传、Git 操作不在脚本内完成。
