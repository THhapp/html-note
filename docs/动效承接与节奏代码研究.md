# 动效承接与节奏的代码研究

> 资料定位：研究记录（非现行 API），不是接口规范。
> 本文记录 2026-10-30 对开源实现、当前工程源码与本机播放观测的研究证据。
> 现行接口见 [公共编排层](公共编排层.md)；设计取舍见 [公共层设计与取舍](公共过渡能力设计.md)；维护布局见 [架构与接口](架构与接口.md)。

研究日期：2026-10-30。范围是承接、重叠、错开、可见时机、缓动、空间连续性与完成管理的具体代码。本文保留研究证据；设计与实现的取舍见[公共层设计与取舍](公共过渡能力设计.md)。研究阶段未修改产品或重选动画引擎。

本研究重新通过 GitHub 连接器读取固定提交源码，不仅复述前一轮调研。执行了位置解析函数、精简 flow 协议、缓动数值和当前 Matrix 标签快照的针对性探针。2026-10-30 随后以真实 Edge 对本机两个预览做了补充播放观测（不修改产品源码）；实测数据、截图判读和修正见第 14 节。

## 1. 核心发现

1. 目前 after 表达的是“上一组 ready 动画全部完成后启动”，尚无 Binding 级“与某段同起点”“从某段开始稍后接入”“结束前接入”。这几类关系在成熟实现中有明确区别。
2. 总时长、动画启动时刻与新内容首次可见时刻不同。当前乘积有内部160ms保持和55%的新值透明阶段，放在整段Matrix等待之后会叠加成明显延后。
3. 平滑的缓出尾部适合自然停稳，但整段尾部不一定都应阻塞下一个配合动作。不能仅凭“ready”命名认定这一点已经解决。
4. 获认可例子的主要变化共享一轮目标布局，通过少量关系延后配合；它们没有把所有动作都改成严格串行。
5. 流利还依赖真实前态、稳定身份、属性归属和批量读写。并非所有不顺畅都是时长问题，也没有足够证据将当前感受归因为掉帧。
6. 当前另有可复现的快照问题：Matrix源快照保存了可变flagEl引用，提交后再读hidden会把新可见状态误当旧状态，漏掉标签入场计划。

研究支持先区分时间关系和可见变化，再判断有限的公共表达方式；本文不据此冻结字段。

## 3. 研究时的当前工程：到底在等待什么

### 3.1 ready仍以选定动画的finished计算

`src/demo/scene.js`（研究时路径）：

- planAdapterEffects按gate把句柄放入readyHandles/finishHandles。
- startMember对readyHandles执行Promise.all(handle.finished)后resolve ready。
- scheduleMembers等待所引用Binding.ready，之后才play下一参与者。

这能区分一部分提示尾部与内容效果，但Matrix.planCueStyles把全部520ms样式过渡放入ready。它没有把“必要关注已建立”与“背景等仍在收尾”分别表达。

当前after也是整个Binding的门槛。它不知道作者只是希望两个相关动作略有先后，并非希望后者等前者完全结束。

### 3.2 首步源码时序探针

读取实际DEFAULTS、Matrix时长和Sequence新值keyframe后计算：

| 时点 | 源码估算 | 依据 |
| --- | ---: | --- |
| Matrix开始 | 0ms | 无after |
| Matrix ready / 乘积开始 | 520ms | Matrix样式渐变整段gate:ready |
| 乘积新值开始显现 | 911ms | 520 + 160 + 420×0.55 |
| 乘积新值完整 / 求和开始 | 1100ms | 520 + 160 + 420 |
| 首个求和新值开始显现 | 1226ms | 1100 + 420×0.3 |
| 首个求和替换结束 | 1520ms | 1100 + 420 |

这段时间不是纯空白：源值仍保留，部分颜色也可能变化。但从点击到新的乘积出现，已有约0.91秒；单独看每段动画时长无法发现这种积累。

以上不包含rAF、布局、Promise调度和渲染成本，不是浏览器计时。后续停点因新增项、FLIP与不变成员不同，不应全部套用这张表。

2026-10-30 真实 Edge 补充观测（第 14 节）测得首步：点击约 2.7ms 返回，Matrix 目标关注在 7ms 已出现，Matrix 样式播放约 6.5—526ms，Sequence 实际启动约 534ms，乘积目标首次不透明约 930ms，求和目标首次不透明约 1257ms，按钮恢复约 1555ms。源码估算的量级成立，且“先等到整段 Matrix 完成后才启动乘积”是主要串行来源。

### 3.3 三类开始条件需要分别看

| 开始条件 | 用途 | 当前支持情况 |
| --- | --- | --- |
| 与某段同一变化窗口，略晚接入 | 关注与相关对象变化配合 | 可同窗；小延后主要写在Adapter内部，缺少跨Binding相对起点 |
| 前段已出现可承接的信息 | 值已可辨后承接下一表达 | gate可选子句柄，但不能直接指出同一动画内部的内容时点 |
| 前段真正完成 | 最终结果、依赖资源、必须落稳的对象 | after及objects-settled已经覆盖 |

这不是要求马上增加三个公共API，而是先防止用一种完成等待替代三种时间关系。

## 4. GSAP：放置时间与结束通知分别处理

源码：[位置解析](https://github.com/greensock/GSAP/blob/13e2b790546426a1a2e0e9b409f3f8dc6d6611f2/src/gsap-core.js#L389)、[加入父时间线](https://github.com/greensock/GSAP/blob/13e2b790546426a1a2e0e9b409f3f8dc6d6611f2/src/gsap-core.js#L287)、[统一渲染](https://github.com/greensock/GSAP/blob/13e2b790546426a1a2e0e9b409f3f8dc6d6611f2/src/gsap-core.js#L1537)。

_parsePosition把相对位置解析成数值；_addToTimeline将位置与子项delay合成_start，计算_end。Timeline.render按父时间计算子项局部时间，不等每个子项的Promise结束后才决定后续何时开始。

因此，后续效果可以在前一个效果的启动后或结束前接入，整体仍有统一结束通知。

执行真实解析函数，输入：总时间线末尾1400ms，最近子项开始140ms、结束660ms，cue标签200ms：

| GSAP位置 | 结果 |
| --- | ---: |
| 省略 | 1400ms |
| < | 140ms |
| > | 660ms |
| <+=0.12 | 260ms |
| -=0.2 | 1200ms |
| cue+=0.08 | 280ms |

注意“时间线末尾”和“最近一个子项结束”也不总是同一时刻，已有较长的重叠轨道时尤其如此。

本项目可借鉴先确定位置、再统一运行和收束。无需为此引入整套GSAP，亦不能忽略其单独许可边界。

## 5. Anime：相同符号可能含义相反

源码：[position.js](https://github.com/juliangarnier/anime/blob/2c9cf8ea00329f6768c7d7902252ed977d75ce42/src/timeline/position.js#L36)、[addTlChild](https://github.com/juliangarnier/anime/blob/2c9cf8ea00329f6768c7d7902252ed977d75ce42/src/timeline/timeline.js#L115)。

getPrevChildOffset区分上一项开始和结束；parseTimelinePosition处理绝对位置、相对值和标签。addTlChild按每项offset+delay+duration的最大值更新父时长，允许子项重叠。

同样的输入中，上一项_offset=100ms、_delay=40ms、duration=520ms：

| Anime位置 | 结果 |
| --- | ---: |
| 省略 | 1400ms |
| < | 660ms |
| << | 140ms |
| <<+=120 | 260ms |
| -=200 | 1200ms |
| cue+=80 | 280ms |

这里的<指结束，GSAP/Motion的<指开始。直接把供应商字符串暴露为公共编排语义容易误用。研究所得是几种时间关系，不是推荐照搬某家的符号或默认参数。

## 6. Motion：先编译属性轨道，再运行

源码：[sequence编译](https://github.com/motiondivision/motion/blob/9ba8846b6819172cb829e65a9f46433a4de377ab/packages/framer-motion/src/animation/sequence/create.ts#L45)、[calc-time](https://github.com/motiondivision/motion/blob/9ba8846b6819172cb829e65a9f46433a4de377ab/packages/framer-motion/src/animation/sequence/utils/calc-time.ts)、[属性区间编辑](https://github.com/motiondivision/motion/blob/9ba8846b6819172cb829e65a9f46433a4de377ab/packages/framer-motion/src/animation/sequence/utils/edit.ts)。

编译器维护prevTime、currentTime和totalDuration。每段把起点与delay、duration组合成绝对时间；最后按元素/属性合并keyframes并归一化offset。最终运行的是已安排好的属性轨道，不是一串依次await。

calcNextTime真实函数的探针输入为current=660ms、prev=140ms、cue=200ms：

| Motion位置 | 结果 |
| --- | ---: |
| < | 140ms |
| <0.12 | 260ms |
| -0.2 | 460ms |
| cue+0.08 | 280ms |
| 数值0.12 | 120ms |

这个current是编译游标；totalDuration另存全局最大末尾。对照GSAP的-=0.2不能只看符号就认为同义。

edit.ts还按元素/属性清除新区间内旧keyframes。值得借鉴的是控制属性归属；不能把“能叠很多动画”当成可以让多个效果随意争写transform。

### 负delay不是追回过去的重叠

先await上一段finished，再用负delay播放下一段，只会让后一段从中途开始；它无法回到过去，与已结束的前段重叠。负delay跳过一部分本地过程的含义，亦见[Motion官方说明](https://motion.dev/docs/stagger#negative-staggers)。

## 7. Motion Canvas：chain、all、sequence是三种调度

源码：[chain](https://github.com/motion-canvas/motion-canvas/blob/7b91435c301d530351dcf5ebb91dd139c002e405/packages/core/src/flow/chain.ts)、[all](https://github.com/motion-canvas/motion-canvas/blob/7b91435c301d530351dcf5ebb91dd139c002e405/packages/core/src/flow/all.ts)、[sequence](https://github.com/motion-canvas/motion-canvas/blob/7b91435c301d530351dcf5ebb91dd139c002e405/packages/core/src/flow/sequence.ts)。

执行这三个真实generator的函数体，使用精简wait/join协议，不加载渲染器。三项各400ms：

| 组合 | A/B/C开始 | 总时长 |
| --- | --- | ---: |
| chain | 0/400/800ms | 1200ms |
| all | 0/0/0ms | 400ms |
| sequence，间隔100ms | 0/100/200ms | 600ms |

后一种没有缩短每项动作，也没有要求同时变化。区别在于间隔决定启动，最终join负责等待。

边界探针：三项各20ms、间隔100ms时，最后一项220ms结束，sequence直到300ms才返回。源码在最后一次启动后仍waitFor，因此有80ms尾部等待。它证明这种方法有价值，也证明不能照抄其循环就认为天然无空等。

精简协议只验证调度含义，不等于运行了完整Motion Canvas线程、逻辑时钟或浏览器。

## 8. Reveal：同一过渡内组织主变化与新增内容

源码：[AutoAnimate.run](https://github.com/hakimel/reveal.js/blob/e240e175232fa2de660a02bc0d7bf5f655b159bb/js/controllers/autoanimate.js#L24)、[选项继承](https://github.com/hakimel/reveal.js/blob/e240e175232fa2de660a02bc0d7bf5f655b159bb/js/controllers/autoanimate.js#L292)。

run先配对和生成目标样式，一次写入CSS，再在下一帧切换running；未配对的新内容默认在总过渡的20%时接入，并用80%的时长淡入。它不等匹配对象全部结束才加入新内容。

父级默认、继承值、元素覆盖和matcher覆盖各有位置，这与当前Matrix/Expression内部固定时长、公共timing难以调节的情况不同。

它还主动让出Fragment管理的opacity，避免两个系统争夺。这里值得提炼的是同一次过渡组织多个角色与属性归属，不是采用20%/80%作为所有知识演示的比例。

## 9. Shiki：批量准备、局部延后、统一启动与收束

源码：[renderer](https://github.com/shikijs/shiki/blob/f7d0167873fd676fe4e190bc9b53832fba9ee01d/packages/magic-move/src/renderer.ts#L188)、[CSS](https://github.com/shikijs/shiki/blob/f7d0167873fd676fe4e190bc9b53832fba9ee01d/packages/magic-move/src/style.css)。

render按key复用元素，测量旧位置，形成目标children与离场节点，批量写目标、准备反向位移/进入/退出，再强制reflow并统一执行postReflow。结束监听在新transition形成后收集getAnimations，避免读到空动画集合。

其默认duration=500ms、stagger=0时，CSS比例得到：

| 角色 | 计算开始 | 计算结束 |
| --- | ---: | ---: |
| 离开 | 50ms | 550ms |
| 移动 | 150ms | 650ms |
| 容器 | 200ms | 700ms |
| 进入 | 350ms | 850ms |

这是参数计算，不是实际回放。几类效果部分重叠，由最后真实句柄收束。

同一套duration与delay比例可以协调局部效果，但默认进入延后350ms并不自动适合本项目。CSS中的transition:all亦不应无条件搬入通用组件。

## 10. 认可示例具体做对了什么

### 10.1 透明传输第二版

原 HTML（本地历史样本，不随仓库分发）的renderStep先提交完整目标布局。按稳定token key同时补旧到新位移；新增chip和替换提示随同一次DOM更新发生。括线下一rAF定位，再按局部延后进入。

源码安排为：位移340ms、chip进入340ms、替换提示550ms、括线延后120ms再380ms。它们围绕同一条数据线重叠，不是340+340+550+380的队列。

字幕和结果保留，图元位置与身份连续，帮助读者回看。旧实现缺少当前要求的完整取消、执行态和可靠完成边界，不能整体退回旧播放器。

### 10.2 保留的R10序列插入

`src/viz/sequence-insert.js`（研究时路径）的 animateInsert：

- 让位从最右开始，按元素间隔20ms启动，每项320ms。
- 新卡落位360ms，与让位同窗；虚实颜色变化240ms也在其中。
- 插入符在120ms后淡出160ms。
- 括线在需要让位的那组shiftEnd后再接入，而非等待整套演示的所有效果。

例如原序列5项、在第3项前插入时，三项让位从0/20/40ms起，落位也从0开始；括线接续让位。这是围绕同一操作的配合，并非每个视觉属性各排一个阶段。

当前R10另保留minTrip和settlePad；它们不应提炼成新公共层的最短等待标准。这里读取的是保留实现，不声称重新播放了最初获评版本。

## 11. 缓动与有效可见时间

用二分求解cubic-bezier的x，再计算y；没有用y直接替代时间。结果是插值进度，不是人的理解进度。

| 曲线 | 时间25%时的插值 | 时间50%时的插值 | 到达90%插值所用时间 |
| --- | ---: | ---: | ---: |
| 当前(.3,0,.15,1) | 38.84% | 81.91% | 60.48% |
| 较早(.2,.7,.2,1) | 72.74% | 92.96% | 43.64% |
| R10(.22,.68,.24,1) | 68.48% | 91.71% | 46.62% |

当前520ms关注渐变，约314.5ms到达90%插值，余下约205.5ms继续缓慢趋稳。温和收尾本身合理；若其全部末尾都阻塞后续，配合动作会显得逐段停住。

不能据此规定“90%就是ready”。颜色、位移和文本显现的可辨条件不同。

当前Sequence的线性keyframes更直接：delay160ms，新文字在420ms交换的55%位置前一直透明，局部首次可见是391ms。这个保持如果与主要位移重叠，可以服务追踪；若之前已经等完一段关注，则再次累计延迟。

因此，需要同时查看：启动、首次可见、主要变化、完整可读与收尾。一个总duration数字或统一调快并不能说明这些关系。

## 12. 另外发现的实现问题与风险

### 12.1 已由纯函数探针复现：源标签可见性不是快照

`src/demo/adapters/matrix.js`（研究时路径）的 captureSnapshot 保存 flagEl 引用，planFlagEntries在commit后读取source.flagEl.hidden。

探针执行实际planFlagEntries函数：

| 输入情形 | 计划的标签进入效果数 |
| --- | ---: |
| 源flag起初隐藏，同一节点commit后可见 | 0 |
| 源可见性冻结为hidden:true，目标可见 | 1 |

前态引用随着DOM一起变化，误判新标签原本已可见。此结果只证明标签规划缺陷，不证明所有关注过渡缺失。显示冗余标签本身也应另外处理，不能通过修好它的动画代替表达判断。

2026-10-30 真实 Edge 复核确认该缺陷在组件上也成立：第二过渡点击后约 4ms，旧单元 flag 立即 hidden、新单元 flag 立即 visible，flag opacity 全程为 1；采样到的动画中没有以 .nviz-matrix__cellflag 为目标的动画。old/new 单元的背景和轮廓仍在约 520ms 的样式渐变中，所以屏幕上出现的是“文字角标瞬间切换、颜色随后慢慢追”的混合状态。见第 14 节。

### 12.2 连续与离散样式混在一起

Matrix STYLE_PROPS包含颜色、opacity，也包含outlineStyle等关键字。给整组统一520ms不代表每个属性都能连续变化。关键字无法连续插值时会有离散交替，见[MDN动画组合规则](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Animations/Animatable_properties)和[outline-style定义](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/outline-style)。

可研究固定轮廓类型、只变化透明度/颜色/几何，或使用单独提示载体；这仍需实际观看，不把一种轮廓强制为全库样式。

真实浏览器采样确认：Matrix 的同一组 520ms 动画 keyframes 中确实同时包含 border 各边颜色、outlineColor、outlineWidth、outlineOffset 和 outlineStyle；outlineStyle 是离散关键字，不能连续插值。也就是说“同一 duration”并不等于所有属性都连续。现有采样不能判定它是否是用户感知的主要来源，但它是已确认的混用风险。

### 12.3 Expression的旧值副本与布局载体分离

Expression的layout/content/value目前返回同一个元素；交换旧值用fixed ghost。Sequence的ghost则位于随对象移动的载体内。

表达式某项同时移动和值变化时，fixed旧值副本不天然跟随该项运动，空间连续性与Sequence不同。未来同一项若再使用transform内容效果，也可能与FLIP争属性。

目前尚未通过浏览器确认其实际观感或冲突，不能直接宣布这是当前卡顿的根因。

### 12.4 准备开销与播放衔接分开

当前Matrix重组表格结构但复用单元，Expression项重建、逐项几何/样式读取存在准备成本；当前的规划顺序也会交错测量与预置动画。Shiki提供了批量准备的具体参考。

但小规模矩阵是否因此产生掉帧，需要真实rAF/性能证据。随后的补充观测（144Hz 左右的 headless Edge，1280 宽）得到 rAF 间隔中位数约 6.9ms、p95 约 7.0—7.1ms；一次 Matrix 过渡最大 23.8ms，一次 Sequence 过渡最大 34.5ms，均未出现持续掉帧。点击同步处理约 1.3—2.7ms。因此当前可见的“卡”更符合串行等待、内部 160ms 保持和文字角标瞬切，而不是持续掉帧；这个结论只限本机环境，不是通用性能结论。

### 12.5 静默失败影响动效判断

scene.createAnimation创建失败会返回finished已解决的空句柄。这样逻辑可继续，但一次必要动画未实际创建时，仍可能被后续当作完成。

研究阶段未触发真实浏览器创建失败；这条路径只作为诊断边界记录。不能仅用 Promise 完成断言证明“确实有过渡”。

## 13. 研究时接口的能力判断

| 所需表达 | 已有能力 | 限制 |
| --- | --- | --- |
| 真正完成后启动 | after / gate / finished | 可以表达，需正确挑选阻塞效果 |
| 多成员同窗开始 | 无after成员 | 可以表达 |
| 成员内部的小错开 | EffectSpec delay / stagger | 可以表达；部分Adapter固定参数，组合层调节不足 |
| 与另一成员起点相关的小错开 | 缺少直接表达 | 目前往往只能移除after后在内部手写delay |
| 前段结束前接入 | 缺少直接表达 | 不能靠已await结束后的负delay补回 |
| 同一动画内某内容时刻承接 | gate只等完整句柄 | 可拆有意义子效果；不能仅把整段标ready |
| 同一源目标下保持连续空间身份 | 部分组件已有 | Expression、提示层和前态冻结仍需完善 |
| 文本角标与视觉 cue 的同一交接 | 组件内部 rail；Adapter effect | 当前 flag 源状态读取错误，见 12.1 |
| 外部 timing 调整 Adapter 内部节奏 | 传给 effects 的 ctx.timing | Matrix/Expression/DOM 的部分 durations 仍硬编码；实测 scene timing=80 时 Matrix 仍播放 520、Expression 仍播放 360 |

其中前三项可以先用已有能力改善；后面几项才是考虑有限公共增补的证据。研究不支持立即引入完整时间线语言或第三方引擎。

研究后的共同前提：先按“首次可见—主要变化—收尾”审视代表过程，围绕同一知识对象组织效果，再判断是否需要有限的公共表达；内部微动作不逐个拆成点击，保留读者推进与停稳证据。

## 14. 真实播放观测（2026-10-30）

### 14.1 方法与环境

- 使用本机 Edge（headless）、file:// 打开已构建的 dist/公共层复用验证-矩阵乘法.html 与 dist/公共编排层-整合预览.html，不修改产品源码、样例或构建产物。
- 用页面内 requestAnimationFrame 逐帧采样：按钮状态、字幕、复制后的矩阵单元、Sequence 值/ghost、Expression 部件、结果容器、DOM 起止标记，以及 document.getAnimations 的真实时间轴。
- 用 getComputedStyle 记录关键单元的 background、outline、flag 可见性；截图用于核对同一时点的视觉组合。
- 临时探针放在 _dev/motion-research，任务结束删除。采样环境为约 144Hz 的 headless Edge、1280 宽；所有毫秒是近似值，不代表用户显示器。
- 选中矩阵第一步（locate→pair1）和后续一步（pair1→pair2），并与已认可的字节样例 raw→stuffed 对照。

### 14.2 矩阵首步与后续步实测

点击返回同步处理约 1.3—2.7ms。主要时点（相对点击）：

| 事件 | 首步 | 后续步 | 依据 |
| --- | ---: | ---: | --- |
| Matrix 目标直接关注写入 DOM | 7ms | 4ms | data-direct-mark / cellflag 已切换 |
| Matrix 样式动画开始 | 6.5ms | 4.8ms | 全部 520ms，0 delay |
| Matrix 样式动画结束 | 约526ms | 约525ms | animation finished |
| Sequence 效果实际开始播放 | 约534ms | 约526ms | 预置后由 after 放行 |
| 乘积新值首次不透明（>0.02） | 约930ms | 约929ms | 目标 value opacity |
| Sequence 整段值替换完成 | 约1114ms | 约1100ms | 开始+160 delay+420 duration |
| Expression 求和效果开始 | 约1124ms | 约1116ms | after terms ready |
| 求和第一项目标首次可见 | 约1257ms（p1 4） | 约1124ms 起（新项进入） | 目标 opacity / 新部件 |
| 下一步按钮恢复 | 约1555ms | 约1491ms | aria-disabled 变 null |

关键事实：

1. after 等的是 Matrix 的整个 520ms ready 手柄；点击后到 Sequence 开始约 0.53s。Sequence 内部再有 160ms 延迟，点击到首个乘积可辨约 0.93s；求和第一项可辨约 1.26s。源码估算的 911/1226ms 基本成立，实测略长。
2. 在约 250—520ms 的区间，矩阵的直接关注已经出现且颜色基本稳定，但乘积卡仍是原值，累计和仍是“—”。截图在 450/560ms 看到的正是“矩阵已经落位、计算区没有承接”的空档；这不是 rAF 掉帧，而是串行启动造成的视觉停顿。
3. 下一步按钮在 1.5s 左右才恢复；最后一段是 Expression 与收尾衰减，约 0.3s 尾部。它本身不算空等，但与前面 0.53s 等待叠加后，总过程超过 1.5s。

### 14.3 字节样例对照

同一采样方法下，已认可的 byte raw→stuffed：

| 事件 | 实测 |
| --- | ---: |
| 新插入 chip 首次可见 | 约7ms（新 chip 与让位同窗） |
| p1/p2 新值首次可见 | 约399/440ms |
| 关系括线出现 | 约232ms |
| 接收端结果显现 | 约628ms |
| 场景 idle（最终帧按钮按设计保持不可用） | 约906ms |

byte 的可接受节奏不是“等 layout 全部结束再做值交换”，而是让位、插入、值替换、括线和结果在 0—0.9s 内相互重叠。矩阵当前是“Matrix 完成 → Sequence 完成 → Expression 开始”的三段链；用户感知的“卡顿”更符合这个结构，而不是帧率。

### 14.4 “关注”角标的真实行为

第二过渡前，old pair A11/B12 为直接关注，背景约 rgb(238,242,255)、outline 约 rgb(49,92,218)，cellflag 可见文字“关注”；target pair A12/B22 为 none、flag hidden。

点击后：

- 约4—20ms，old pair 的 data-direct-mark 已为 none，flag 立即 hidden；target pair 已为 focus，flag 立即 visible，flag opacity 恒为 1。
- 采样到的动画中没有以 .nviz-matrix__cellflag 为目标的动画；因此新角标不是“快速进入”，而是直接出现。
- old pair 的 background/outline 仍在从旧值向普通单元渐变；约520ms 才落到 rgb(244,246,249)/rgb(32,41,56)。target pair 的 background/outline 才从源值过渡到 rgb(238,242,255)/rgb(49,92,218)。
- 屏幕上同一时刻出现“文字状态已经跳过去、颜色还在追”的混合；old 的文字先消失、颜色后消失，new 的文字先出现、颜色后稳定。

可见标签总数：行头“关注”、列头“关注”、两个当前单元 pill 各“关注”。Matrix 的 summary:false 只隐藏表格下方的汇总句，不隐藏这些行头/单元标签。组件源码中 markLabel 在 Matrix render 中直接写入 headmark 和 cellflag；不是样例 CSS 补丁。

### 14.5 源快照问题已由真实组件复现

Matrix Adapter 的 captureSnapshot 保存的是 source.flagEl 这个可变节点引用；commit 复用同一 cell/flag 节点并更新 hidden，effects 规划时再读 source.flagEl.hidden：

| 位置 | 代码行为 | 结果 |
| --- | --- | --- |
| src/demo/adapters/matrix.js:251—271 | 快照保存 flagEl 引用，不保存 hidden 布尔值 | 源态跟随后续 DOM 改写 |
| 同文件:330—342 | commit 后读取 source.flagEl.hidden | target 新 flag 被误判为“源已可见”，不产生进入计划 |
| src/viz/objects.js:1181—1216 | 同行列单元复用 td/flag，更新 hidden/textContent | 上述引用确实被改写 |

因此有两个独立问题：一是角标视觉本身过度；二是即使决定保留角标，其源/目标可见性管理也不可靠。两者不能用一个动画补丁互相掩盖。

### 14.6 外部 timing 与硬编码参数

用临时定义把 scene.timing 设为 duration:80、valueSwapDelay:10、easing:linear，Matrix 与 Expression 的实测量：

| Adapter | scene timing 请求 | 实际动画 |
| --- | --- | --- |
| Matrix cue | 80ms/linear | 520ms/cubic-bezier(.3,0,.15,1) |
| Matrix flag entry | 80ms | 180ms（且本次因快照问题未创建） |
| Matrix value | 10/100ms | 80ms delay / 320—360ms + 后续 |
| Expression enter | 80ms/linear | 360ms/cubic-bezier |
| Expression value/ghost | 10/100ms | 420ms/linear |

结论：frame/layout 与 reveal 的 timing 能调整，但 Matrix/Expression 的大量内容效果没有使用 effectCtx.timing（DOM Adapter 源码中同样固定为420ms，本次未单独测时）；公共 timing 目前不能作为跨成员的统一节奏旋钮。Matrix 的 keyframes 还同时包含离散 outlineStyle，进一步说明“统一 duration”不等于所有属性连续。

### 14.7 帧间隔与准备成本

- Matrix 首步：rAF 中位约6.9ms、p95约7.1ms、最大23.8ms；没有超过25ms的采样帧。
- Matrix 后续步：中位约6.9ms、p95约7.0ms、最大7.8ms。
- byte：中位约6.9ms、p95约7.1ms、最大34.5ms，仅1次超过25ms。
- 点击同步处理1.3—2.7ms；没有观察到与整表重建相对应的持续主线程阻塞。

所以：本机证据不支持“掉帧是主要根因”。准备成本仍需在低端设备验证，但当前观感应优先按串行等待、角标瞬切、内部保持与过重的 ready 门槛解释。Expression 固定 ghost 与 FLIP 的冲突、Matrix 局部重组在更复杂内容下的成本，仍未被证实。

### 14.8 已证实 / 未证实

已证实：

- 当前矩阵样例存在约0.53s的 Matrix 整段等待，加上 Sequence 内部延迟后，点击到首个乘积可辨约0.93s；求和约1.26s；总按钮约1.5s。
- 已认可 byte 样例在约0—0.9s内让多个变化重叠完成；差异是组合方式，不是帧率。
- 可见“关注”角标为组件默认文字，summary:false 不能关闭。
- 新角标直接出现、旧角标直接消失；源 flag 快照引用在 commit 后被改写，进入动画缺失。
- Matrix/Expression 多个效果硬编码时长，scene timing 请求未被采用；Matrix keyframes 混有离散属性。
- 本机 rAF 没有持续丢帧。

未证实、不能写成根因：

- Expression fixed ghost 与 FLIP 的实际视觉冲突（当前样例中尚未稳定复现）。
- 矩阵整表重组、样式计算导致用户设备掉帧；本机没有证据，需更低性能/更长矩阵样本。
- outlineStyle 的离散交界是否单独造成明显跳变；它被包含在动画里，但当前主要可见跳变来自角标文字和串行空档。
- 用户设备/浏览器/显示刷新率与实际主观感受；本机 headless 数据只用于解释机制。

### 16.1 复用实现的准确边界

[Shiki render](https://github.com/shikijs/shiki/blob/f7d0167873fd676fe4e190bc9b53832fba9ee01d/packages/magic-move/src/renderer.ts#L188)以同步函数完成旧布局捕获、目标更新、反向起点与postReflow；它的新效果建立后才聚合动画。可借鉴批量事务和稳定key，不把其previousPromises.resolve当作底层cancel，不扫描本工程宿主的全部getAnimations。

[Reveal AutoAnimate](https://github.com/hakimel/reveal.js/blob/e240e175232fa2de660a02bc0d7bf5f655b159bb/js/controllers/autoanimate.js)为fragment主动让出opacity控制，支持明确的属性归属。本工程用载体分层避免争写，不需要搬整套属性编译器。

[Web Animations ready](https://www.w3.org/TR/web-animations-1/#the-current-ready-promise)是play/pause准备，和NoteDemo.ready不同；[finished/cancel](https://www.w3.org/TR/web-animations-1/#the-current-finished-promise)要求捕获本次Promise并区分取消。整体easing会重映射关键帧offset对应的时间，[关键帧自身easing](https://www.w3.org/TR/web-animations-1/#the-effect-value-of-a-keyframe-effect)又作用于区间；值交换保持段不能被统一缓动无意压缩。

Anime/Motion/Shiki/Reveal 的固定版本为 MIT，GSAP 为其自身 Standard 许可。本工程的取舍是优先复用本库 Sequence 与自写窄适配、不新增运行时依赖；实际复制代码才按来源处理许可。

### 16.2 未变成已证实根因的风险

Expression 旧副本在移动与换值同时发生时的空间漂移，仍需代表夹具观察。当前新增项没有sourceRect，因此不能仅因layout/content字段相同就断言现有每次入场必然与FLIP冲突；分层是为补齐安全可组合能力。

outlineStyle 离散插值、复杂表格准备成本、用户设备帧率的影响仍不得夸大；应在具体受影响情形下验证，不为个人项目建设全面性能平台。
